## 可用流程

首页“项目模拟面试”或导航“模拟”进入 [模拟列表](http://localhost:3000/mock-interviews)。选择 VendorGuard 或发票实习及一个主问题，明确开始后才创建轮次；列表显示最近 20 轮，可继续进行中的模拟或查看已结束总结。

每轮固定五个节点：自我介绍 / 职责 → 主问题 → 追问 1 → 追问 2 → 追问 3。主问题只来自启用、身份与正文版本匹配结构化来源的“简历实战”题，三个追问直接取既有内容；职责提示要求本人区分独立完成、复用与协作的边界。手机选择器下方展示完整主问题，避免长题干截断。

每个节点可填写回答或口头简记、选择五类本人卡点并填写说明，可选手动计时。计时仅累计页面可见时的秒数，刷新默认暂停；不代表正确程度。点击“保存并继续”记为已答，空文字明确保留为口头已答；“跳过本节点”保留已有简记但记为跳过。

“保存草稿并暂停”保存当前节点，显示成功反馈；从列表或原轮次 URL 可继续。提前结束会保留当前草稿为未答，其余待答节点也保留为未答。已结束轮次固定保留，不能重开；可另开新轮。

总结区分已答、跳过、未答、口头无简记、本人表达卡点和需补证据节点。结束后统一显示参考快照、全部提问及记录，提供主问题、个人回答卡和建议基础的正式补练入口。基础建议按主问题所属分类选取已有关联基础，缺少同分类候选时使用现有基础路径，最多三题。

## 保存与隔离契约

开始时保存题干、追问、参考和基础建议快照。种子更新、正文修改、停用题目或修改目标均不改已开始的轮次。进行中的轮次 DTO 只发送当前及过去节点，未来追问题干、参考和基础建议留在服务端；结束后才发送完整内容。

| 数据或操作           | 实际行为                                                                                        |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| `mock_rounds`        | 用户、项目、来源主问题、创建 requestId、参考与基础建议快照、revision、开始 / 更新时间与结束时间 |
| `mock_nodes`         | 固定位置、父节点与来源题、提问快照、回答、已答 / 跳过 / 未答、计时、本人卡点与说明              |
| `mock_round_actions` | 每轮 requestId 与规范化请求，持久保存重试依据                                                   |
| 创建轮次             | 锁用户；同 requestId 同选择返回原轮次，不同选择返回 409；停用 / 版本失配题不能新建              |
| 节点操作             | 锁轮次、检查 revision 与当前节点；节点、轮次与请求记录在同一事务保存，失败回滚                  |
| 重试与并发           | 同请求含迟到重试不重复推进；不同内容、旧版本、未来位置及倒退计时返回 409 并提供当前服务器轮次   |
| 未保存编辑           | 独立浏览器草稿键，按轮次和节点隔离；服务异常保留同一次请求，确定冲突保留文字供本人核对 / 合并   |

已保存模拟记录从数据库读取，浏览器存储仅用于未保存编辑和待确认请求。另一页面的 storage 事件不会覆盖当前正在编辑的文字；版本冲突须先核对，再采用服务器记录或确认保留本地编辑。存储不可用时仅承诺当前页保留最新编辑，界面提示保存到服务器。

接口为 `POST /api/mock-interviews`、`GET /api/mock-interviews/[id]`、`PUT /api/mock-interviews/[id]`。PUT 支持 draft、answer、skip、finish；回答最多 10,000 字符、卡点说明最多 2,000 字符、累计计时 0–86,400 秒。所有模拟操作均不写普通 `review_events`，不改自评、次数、复习安排或 W4 正式覆盖。模拟卡点留在节点中；需要长期跟进时由本人进入题目详情主动保存 W3 卡点。

## 增量迁移与个人库

新增冻结迁移 `src/db/migrations/0002_mock_interview.sql`，通过 `migrate-mock-interview.ts` 与 `pnpm db:migrate:w5` 运行。无参数只显示说明、不连接数据库；加 `--apply` 才执行。它要求既有 W0 迁移记录及 checksum 一致，使用与 W0 相同的 advisory lock 串行升级；拒绝无迁移记录的同名表，DDL 与版本记录在一个事务内保存。重复执行不改数据，已应用文件不得改写；新空库继续使用 `db:push` 建完整 Schema。

2026-10-12 已先保存升级前十表完整 Schema / 数据恢复包，在独立 PostgreSQL 实际恢复，比较字段、默认值、约束、索引、全记录和四个序列，再演练 W5 升级。恢复与升级均通过后才迁移个人库。原九张业务表全字段与四个序列保留，原 W0 迁移记录不变，只新增 W5 版本和三张空模拟表；个人库未运行 seed、`db:push` 或验收写入。

证据位于 `.local/backups/job-seeker-w5-20261012/`：

- `records-before.json`：升级前十表与四个序列。
- `restore-pre-w5.sql`：升级前完整 Schema / 数据恢复包，仅向空库恢复。
- `rehearsal.json`：独立恢复、Schema / 记录 / 序列比对与 W5 升级结果。

这份恢复包覆盖 W5 升级前状态；之后新增的模拟资料仍需 W7 的统一备份与导出。
