## 检查范围与计数规则

全量检查源码中的 670 道题，并只读比对个人数据库的 670 道启用题；题干和答案逐项一致。表述检查定向抽查 18 题的完整讲解，并补充审阅 25 题简历要点，覆盖普通题、扩展题、基础题、核心题和简历题。这是针对问题的抽查，不能推算全部答案的语义错误率。

口头短答取“30–60 秒回答”“60–90 秒回答思路”或“核心结论”段落。计数移除 Markdown、标题、空白、标点、链接 URL 和代码块，保留汉字、字母与数字；英文按字母数计，不代表实际发音长度。“全文文字”仍包含准备提示、来源说明和参考资料名称，不等于纯讲解字数。

采用每秒 3–4 个有效文字字符作长度筛查假设，普通题低于 90、简历题低于 180 标记为待补充。这个阈值是本次审查口径，原项目没有定义它；估算未经过真人计时。真实验收需要朗读，不能仅靠字数判定。

逐题数据见 [670 题检查明细](ANSWER_QUALITY_AUDIT_DETAILS.json)，复查脚本见 [audit-answer-quality.ts](../scripts/audit-answer-quality.ts)。明细中的自动提示是候选问题，不是自动质量评分。

## 两个修订示例

以下是本次检查的建议稿，未替换实际答案。它们展示应补的内容和表述方式，不能当作已经验证过的个人项目实现。

### 普通题：类型注解能保证运行时值类型吗

原短答只有 26 个有效文字字符：

> 不能。类型注解不会验证网络 JSON；接收后仍需运行时校验。

建议口头参考：

> 不能。Python 的类型注解主要给编辑器和静态检查工具使用，解释器通常不会因为字典被标成整数值，就逐个检查里面的数据。比如外部 JSON 返回的年龄是字符串“18”，它仍然可能进入这个字典。接收外部数据时，要先用运行时校验器检查字段和类型，再根据配置决定是否接受类型转换。即使已经得到整数，还要检查年龄是否为负、是否超出业务允许范围。类型注解、数据解析和业务校验分别解决不同的问题，不能互相替代。

深入讲解应补一个输入反例、严格与宽松解析的差别、合法整数仍违反业务约束的反例。代码若加入题库，需要实际运行并解释结果。

### 简历题：五个工具如何划分边界

原短答 117 个有效文字字符；原深入要点要求本人“逐一讲”，没有展开工具之间的数据关系。

建议口头参考：

> 五个工具按材料事实、规则结果、制度依据和流程状态分开。材料读取从文件中取得信息，并保留它来自哪里；规则核对使用已有事实做身份、日期等确定性检查；制度检索返回适用条款的原文，供后续报告引用。缺项不能靠模型猜，因此 ask_user 提出需要补充的信息；submit_report 则作为经过校验后的报告出口。这样划分是为了分别回答“材料写了什么”“规则怎么算”和“结论依据是什么”，也方便定位错误。例如证件日期缺失时，应先补材料再核对，不能因为检索到了制度就认定日期合格。模型负责提出工具调用，宿主仍负责参数检查和实际执行；模型生成一段自然语言，也不等于报告已经提交。具体参数名和返回字段需要按真实源码说明。

深入讲解应提供五工具的职责表、事实如何传给核对、检索证据怎样用于提交、追问与提交为什么是状态出口。表中的真实 API 字段仍需核对 VendorGuard 源码；缺少证据的地方不能编造。

## 修订顺序与验收标准

优先修订直接影响当前练习的 30 道核心题和 63 道 P0 简历题，再处理 70 道基础题与其余简历题。扩展题按主题处理，每题单独说明它问的机制，避免在共享段落后添加更多通用文字。

建议普通口头答案以约 120–180 个有效文字字符为起点，简历以约 240–270 为起点，再按实际朗读调整。这些范围用于起草，不是硬性填充要求；简单定义可以保留一句摘要，另提供完整口头参考，不把摘要误标为整段时长。

每题验收要求：直接回答问题，解释至少一个因果或执行过程，给出与本题对应的例子及判断结果，说明必要边界。术语第一次出现时用中文解释；代码和个人履历事实分别验证。自动长度检查只能拦截明显缺失，清晰度、准确性和面试可讲述性仍需逐题审阅。
