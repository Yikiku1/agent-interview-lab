# 求职者训练闭环开发计划

编写日期：2026-10-09（北京时间）
依据：[求职者视角的产品分析与需求](JOB_SEEKER_REQUIREMENTS.md)
计划状态：待实施；本文是开发计划，不代表功能已经完成、排期已经批准或工期已经承诺。

## 1. 目标与交付边界

本计划把需求文档转成一条可逐步验收的产品路径：

> 选择简历或项目范围 → 开始 3 / 5 题短轮 → 独立作答 → 查看分层参考 → 保存自己的回答 → 记录具体卡点 → 按卡点补练 → 查看当前范围覆盖。

首期交付这条日常闭环，覆盖 R01、R03、R04、R05，配套交付 R02 的预设路径与 3 / 5 题短轮，以及 R07 的范围覆盖最小版。它应让用户不需要手工搜索“简历 P0”，也不需要先刷完通用 30 道核心题。

第二期加入 R06 模拟面试、R08 真实面试复盘，以及 R07 的回答变化和反复卡点。R09 作为可独立交付的本地启动、备份和导出能力；R10 只在真实使用暴露出对应需求后评估。

首期不包含自动解析简历、动态 AI 评分、录音转写、登录、云同步、多人排行榜、投递管理或复杂 Agent 编排。

## 2. 当前基线

截至 2026-10-09 已核对以下事实：

- 题库有 670 道启用题，其中简历专项 100 道：P0 63、P1 32、P2 5；按范围为 VendorGuard 60、发票实习 13、综合 5、技术基础 22。
- src/db/resume-content.ts 已有统一的简历来源、场景性质、60–90 秒回答思路、三个要点、证据准备、三个追问和易错点结构；src/db/resume-questions.ts 负责生成种子 Markdown。
- 当前题库筛选只支持题干、分类、难度和掌握状态；项目、简历优先级、回答性质还不能作为筛选条件。
- 首页的今日推荐仍按“到期复习 → 薄弱巩固 → 固定核心新题”工作；简历专项题不会自动作为核心新题。
- users、questions、user_question_progress、review_events 是当前四张表；尚无目标配置、个人回答卡、要点检查、卡点、模拟轮次或真实面试复盘实体。
- POST /api/attempts 已按用户和 attemptId 幂等，正式完成事件为 review_events.kind = 'practice'；URL 固定队列、浏览器草稿、刷新续练和成功响应丢失恢复已有约定。
- 当前轮次只支持 10 / 20 题；练习页面对核心题使用分层答案组件，对其他题展示完整 Markdown。
- 项目是 Next.js 16.3.6、React 19、TypeScript strict、Drizzle ORM、PostgreSQL 的本地单用户应用，固定用户为 default，没有模型服务。

以上是当前代码和数据快照。实现前仍需按 PROJECT_CONTEXT.md、实际源码和运行状态重新确认。

## 4. W0：固定产品和数据契约

### 4.1 首期用户流程

首页提供三个直接入口：

- “简历重点”：全部简历专项题，可进一步选项目和内容优先级。
- “项目讲述”：VendorGuard、发票实习、综合讲述。
- “基础补齐”：由简历关联的技术基础题。

练习设置提供相同范围条件，并显示范围题数、实际队列数量和每题入选来源。未配置目标时沿用当前通用练习和今日推荐；保存或修改目标不创建正式练习事件。

首期目标配置支持：

- 预设：通用核心、简历重点、项目讲述、基础补齐。
- 项目范围：VendorGuard、发票实习、综合、技术基础。
- 简历内容优先级：P0、P1、P2。
- 每日可用时间档位：仅用于选择 3 / 5 / 10 / 20 题规模，不把题数换算成承诺分钟数。
- 可选面试日期：首期保存并提示，第二期再用于冲刺视图。

目标切换只改变后续选题和统计范围，不删除或重写已有回答、进度、练习历史和个人卡。

### 4.2 建议的数据结构

实现时以当前 src/db/schema.ts 为准生成迁移。字段名可按现有命名风格微调，但要保留以下语义。

1. learning_targets

   - id、user_id、preset、project_scope、priority、daily_minutes、interview_date、active、created_at、updated_at。
   - 同一用户只允许一个当前 active 目标；切换时保留旧记录或版本信息，不能让历史数据消失。
   - 目标是筛选配置，不与题目掌握状态绑定。

2. personal_answer_cards

   - user_id、question_id 唯一键。
   - short_answer、example、contribution_boundary、evidence、updated_at。
   - 所有字段可为空；不自动填充收益、贡献或实现细节。
   - 种子导入只更新公共题，不能覆盖此表。

3. answer_point_checks

   - id、user_id、question_id、review_event_id 可空、point_text_snapshot、covered、note、created_at。
   - 每次正式作答的检查结果保存为快照；修改个人回答卡不改写历史检查。
   - point_text_snapshot 防止后续公共答案调整后历史记录失去当时语境。

4. practice_gaps

   - id、user_id、question_id、review_event_id 可空、kind、note、resolved_at、created_at。
   - kind 首期固定为 concept（概念不清）、expression（表达卡壳）、evidence（缺少项目证据）、follow_up（追问不会）、other。
   - 一次作答允许多个卡点；卡点记录不增加练习次数。

5. 第二期实体：

   - mock_sessions：轮次、目标项目、当前节点、状态、开始 / 结束时间。
   - mock_session_nodes：顺序、主问题 / 追问 / 基础题类型、来源题目、问题文本快照、回答记录、跳过状态。节点必须保留顺序和独立记录。
   - interview_reviews：面试日期、岗位 / 面试名称、备注。
   - interview_review_questions：问题文本、可空的 question_id、回答摘要、卡点、改进、来源记录。公共题被修改时不覆盖原问题文本。

可选的 goal_id、mock_session_id、interview_review_id 关联字段只在不会破坏现有唯一索引和恢复逻辑时加入；普通 review_events 的正式完成语义保持不变。

### 4.3 筛选和队列契约

扩展 Filters 时保留现有字段，并增加可组合的简历范围：

- track=resume：只选简历专项。
- project=VendorGuard|发票实习|综合|技术基础。
- resumePriority=P0|P1|P2。
- resumeKind=简历实战|基础关联|扩展设计。

筛选条件进入 URL，题库列表、练习设置中的范围题数和固定队列必须调用同一套条件构造函数，不能分别实现三套近似逻辑。显示优先级和难度两个不同维度，避免把简历 P0 误当成题目难度。

新轮次将 roundSize 扩展为 3、5、10、20；PracticeMode、URL 解析、首页入口和总结页面同步更新。3 / 5 题仍使用现有 roundId、queue、questionId、finished、草稿隔离和 attemptId 幂等。

首期路径的推荐顺序为：

1. 选定范围内的到期题。
2. 选定范围内正式练过且最新状态为不会 / 模糊的题。
3. 选定范围内从未正式练过的题，按简历优先级、项目和稳定题目 ID 排序。

范围外到期题单独提示数量和入口；默认不悄悄占满目标范围的短轮。用户主动点击重练可以突破当天自动推荐排除规则。

- 通用目标不配置时，原有今日推荐、10 / 20 题和继续练习链接保持可用。

## 6. W2：简历答案分层

### 实现任务

- 把 ResumeEntry 的结构化字段作为唯一来源，避免再从生成后的 Markdown 反向解析。
- 在 src/db/resume-content.ts 提供服务端可用的轻量答案对象；内容至少包含依据与边界、短答、三个要点、证据准备、追问、易错点和资料。
- 新增或扩展 ResumeLearningAnswer 展示组件，复用 core-learning-answer.tsx 的可访问折叠模式。
- 练习中默认只显示题目和回答框；用户展开参考后先显示 60–90 秒回答和三个要点，深入拆解、证据、追问和资料按需展开。
- 详情页和练习页使用同一层次；普通题和未结构化题继续显示完整 Markdown。
- 明确“简历实战 / 基础关联 / 扩展设计”的边界，扩展设计使用“如果扩展，我会……”的文案，不把示例当作个人履历。

### W2 验收

- 未主动展开时看不到参考内容；切题后展开状态重置，草稿、自评和提交状态不受影响。
- 短答和要点来自结构化来源；深度内容、代码、资料仍可访问。
- 移动端无横向溢出，代码块可横向滚动，键盘和焦点行为与核心题一致。
- 内容变更不会改变题干身份，不通过改题干来替换已有题目。

## 7. W3：个人回答卡、要点检查、卡点和补练

### 个人回答卡

- 在题目详情、练习总结和历史回答处提供“查看 / 编辑我的回答卡”。
- 支持把某次文字回答复制到卡片后再修改，也支持只填写一句短答或一个卡点。
- 个人卡长期从服务端读取；浏览器草稿只负责未完成当前轮次，不把 localStorage 当长期存储。
- 独立作答时默认隐藏个人卡，防止直接照稿完成。

### 要点检查与卡点

- 参考答案展开后提供三个要点的轻量勾选；勾选表示本人自查，不显示客观评分。
- 允许多选卡点原因和一段补充说明；每次保存时将要点文本快照、选中原因、说明和对应正式回答关联起来。
- 口头作答可以没有全文，但用户仍可保存自查和简记；界面不能声称“系统已核验”。
- 卡点可从总结页、题库详情和目标进度页打开对应补练小轮。

### 接口建议

- GET /api/answer-cards?questionId=...
- PUT /api/answer-cards
- POST /api/practice-observations：保存要点检查和卡点；必须支持重复请求安全处理。
- GET /api/practice-gaps：按类型、项目、目标范围筛选。
- 补练入口复用现有练习 session，只传固定的题目 ID 队列；不复制题目、不改变公共题。

### W3 验收

- 刷新、开启新轮、重启应用后个人卡仍存在；种子导入不覆盖个人卡。
- 从历史回答创建个人卡后，历史 review_events.answer 不变；修改卡片不增加次数、不改变复习安排。
- “概念不清”和“缺少项目证据”可以分别筛选并启动补练；卡点记录能回到题目和当次作答。
- 选择卡点、修改说明和编辑个人卡都不产生正式练习事件；正式提交仍按原 attemptId 幂等。
- 失败恢复、停用题跳过、固定队列和目标中途切换均沿用现有契约。

## 8. W4：首期范围覆盖和端到端验收

### 覆盖计算

新增服务端查询或纯函数，输入当前目标筛选和正式练习事件，输出：

- 当前目标启用题数。
- 其中至少有一次 kind=practice 的独立题数。
- 未正式练过题目列表。
- 当前自评分布。
- 已有个人卡数量。
- 标记为证据齐全的数量（首期可由个人卡 evidence 非空计算，并明确这是本人填写状态）。
- 卡点类型计数和对应补练入口。

覆盖率分子按独立题目数计算，重复作答不增加覆盖；legacy 事件和单独修改掌握状态不计入正式覆盖。目标切换后页面明确当前统计范围；空范围、无记录和无卡点分别显示空状态。不要合并成“面试通过率”。

### W4 首期验收场景

1. 首页选择简历重点，开始 5 题。
2. 完成其中 3 题，提前结束。
3. 留下一个真实项目例子和两条卡点。
4. 刷新并继续原轮，查看回答卡和补练范围。
5. 次日推荐仍沿选定范围推进，且当天正式完成题被排除。
6. 目标切换后原有回答和进度仍可查看，覆盖分母变成新范围。

验收必须同时检查数据库记录和页面结果，不能只看 UI 文字。

## 9. W5：模拟面试与连续追问

### 实现任务

- 从结构化简历题的三个追问生成固定脚本；首版选择 VendorGuard 或发票实习。
- 流程为自我介绍 / 职责 → 主问题 → 追问 1 → 追问 2 → 追问 3 → 总结。
- 每个节点保存独立的回答文字或口头简记、跳过状态、顺序和来源题目；显示当前节点和剩余节点。
- 参考答案在节点完成前隐藏；结束后统一查看主问题、追问、卡点和建议补练。
- 计时仅记录作答过程，不自动推断正确、不自动修改掌握状态、不写普通题 review_events。
- 中断后用模拟轮次 ID 恢复，不与普通练习的浏览器草稿键混用。

### W5 验收

- 至少完成一个主问题和三个已有追问，回答期间看不到后续参考。
- 节点关系、顺序、回答和未答状态都可追溯；刷新或中断后不乱序。
- 三个追问不隐式增加原题三次完成；需要正式练习时必须由用户明确进入普通练习。
- 总结区分未答、表达卡点、缺证据和建议关联基础；没有文字的口头表现不被当作自动评分证据。

## 10. W6：真实面试复盘与补练

### 实现任务

- 新增面试复盘列表、新建和详情页面，最小字段为日期、岗位 / 面试名称、实际问题、回答摘要、卡点和改进。
- 问题可关联已有题，也可保存题库没有的新问题。新问题保留原文，不创建假的公共题目。
- 已有关联题提供“进入补练”，继承参考内容和个人卡入口，但不自动标记正式练过或已掌握。
- 同一公共题可关联多个面试复盘；每次复盘原话和来源独立保存。
- 在 R07 中显示复盘问题的补练状态，不能把“已记录复盘”当作“已完成训练”。

### W6 验收

- 只保存一个新问题也成功；多次面试记录可以区分和追溯。
- 关联已有题后，一键进入固定补练队列；原复盘文字不被题库更新覆盖。
- 复盘、关联、编辑和补练入口均不改变原题的练习次数，除非用户在普通练习中明确完成题目。

## 11. W7：本地启动、备份、恢复和导出

### 启动

提供 Windows PowerShell 启动入口，复用当前 PostgreSQL 和应用：

- 已有服务正常时直接打开页面，不重复占用端口。
- 端口占用、数据库连接失败、应用构建 / 启动失败分别报告原因、检查命令和日志位置。
- 启动过程不能运行种子清理、重置个人数据或覆盖个人回答。

### 数据备份

提供脚本或应用入口，覆盖：

- 目标配置。
- 题目进度和复习安排。
- 正式回答历史和练习事件。
- 个人回答卡、要点检查和卡点。
- 模拟面试和真实面试复盘。

备份文件包含创建时间、应用 / Schema 版本和数据清单。至少完成一次独立临时 PostgreSQL 恢复，逐表比较关键记录数和代表性内容后，才能把它称为“可恢复备份”。

### 可读导出

提供 Markdown 或 JSON 导出供阅读和迁移；明确它与数据库恢复备份的区别。可读导出缺少数据库约束时，不称为可恢复备份。

## 12. W8：R10 按需评估

R10 分开评估，不作为首期依赖：

- JD 定向：保存 JD 和用户选择的技能主题，映射现有题目，允许人工调整，不根据职位名称自动推断全部能力。
- AI 辅助反馈：输入题目要点和本次回答，输出引用原文的建议；未知的项目细节标记为待补证据；失败时手工流程仍可用；不得自动提升自评。
- 录音与转写：用户主动录制，可校对后关联回答；转写失败仍可保存简记；录音和转写状态不等同于回答质量。

只有当首期连续使用记录显示某一成本反复出现时，才为该方向建立独立的小范围方案和数据保留策略。

## 13. 验证计划

### 单元测试

为新增纯逻辑补测试：

- 简历筛选条件解析、组合、空范围和 URL 往返。
- 3 / 5 / 10 / 20 轮次解析与旧 URL 兼容。
- 目标范围推荐的到期 → 薄弱 → 新题优先级、去重、当天排除和范围外提示。
- 覆盖率按独立正式练习题计算，legacy 和状态修改不计入。
- 卡点类型映射、要点快照和补练队列稳定排序。
- 模拟节点顺序、跳过和恢复。

### PostgreSQL 集成测试

继续使用 tests/helpers/postgres.ts 的独立临时数据库，禁止在个人库造验收假记录：

- Schema 创建、外键、唯一约束和目标 / 个人卡 / 观察记录持久化。
- 种子 upsert 后个人表不变。
- 个人卡、要点检查、卡点与历史回答分离。
- POST /api/attempts 的同 ID 重试、同 ID 不同内容 409、并发更新和事务回滚。
- 复盘关联题不创建正式练习事件；模拟节点不改变普通完成计数。
- 备份恢复后逐表核对关键数据。

### 页面和浏览器验收

在可用的 Chrome / Playwright 环境中覆盖：

- 桌面和模拟手机宽度、浅色和深色主题、键盘焦点、减少动画、无横向溢出。
- 首页入口 → 目标选择 → 3 / 5 题 → 提交 → 提前结束 → 刷新续练 → 个人卡 → 卡点补练。
- 参考答案默认隐藏，简历答案分层展开后内容顺序正确。
- 网络失败、提交重试、成功响应丢失恢复、停用队列项跳过。
- 模拟面试不写普通完成，真实复盘关联和补练。
- 控制台无意外错误；HTTP 检查只作为补充，不能替代交互验收。

### 必要静态检查

每个批次按改动范围运行：

pnpm test、pnpm test:db、pnpm lint、TypeScript 检查、pnpm build、git diff --check。
涉及页面交互时增加浏览器验收；涉及备份时增加独立库恢复核对。Next.js API 变更前先阅读当前安装版本 node_modules/next/dist/docs/ 对应指南。

## 14. 不可破坏的现有契约

- 题干仍是种子 upsert 的题目身份；不通过改题干替换题目，不删除有历史的题。
- active=false 仍表示停用；历史进度和事件保留。
- 只有 review_events.kind=practice 是正式完成；目标保存、个人卡、卡点、模拟节点和复盘都不是正式完成。
- attemptId 仍按用户唯一；同 ID 同内容幂等，同 ID 不同内容返回 409；事务、行锁和成功响应丢失恢复继续有效。
- 已开始的固定队列不因掌握状态、目标设置、午夜跨日或首页重新计算而改变。
- 草稿按轮次和题目隔离；独立个人卡不复用当前轮次草稿。
- 今日推荐继续使用北京时间日界线和当天正式完成排除；用户主动重练可显式绕过自动推荐。
- 中文优先、移动端、浅深主题、长时间阅读、键盘操作和错误恢复继续有效。
- 个人数据默认留在本机；不把登录或云端同步作为首期前置条件。

## 15. 每批次完成定义

一个批次只有同时满足以下条件才算完成：

1. 代码、Schema / 迁移、文案和文档与本计划的字段和行为一致。
2. 相关单元、独立 PostgreSQL 集成和静态检查通过。
3. 关键失败路径和恢复路径已验证，个人库没有测试残留。
4. 页面在桌面和移动宽度完成必要交互检查，或在计划中明确记录环境限制。
5. PROJECT_CONTEXT.md 更新当前实现、验证日期、运行状态和未完成事项。
6. 重大交付有对应 docs/ 记录；文档中的数量、链接和“已完成 / 待实施”状态与源码一致。
7. 交付前清理本批次产生且不再需要的临时文件，不自动提交或推送。

## 16. 实施前的决策门

开始 W1 前只需确认以下产品选择，其他实现细节可按本计划推进：

- 首期目标是否默认保存为“简历重点”，还是保持通用核心并由用户主动切换。
- 项目筛选是否保留“综合”作为独立选项；默认首页是否直接进入 VendorGuard。
- 个人回答卡的“证据齐全”是否只由本人勾选，还是首期仅以 evidence 非空表示“已填写”。
- 备份入口首期放在设置页还是提供独立 PowerShell 命令；两者都必须使用同一备份格式和恢复说明。

这些决策不应改变数据隔离、正式完成、固定队列、幂等提交和恢复契约。
